## 3. 流畅度目标与测试条件

**以下数值是工程验收目标，不是已经测得的结果，也不是对所有评委电脑的保证。** 替换旧计划“30FPS即可”的最低线；达到30FPS不能标为操作丝滑。

| 项目 | 首版验收目标 |
| --- | --- |
| 基准环境 | 记录真实演示电脑、CPU/GPU可获取信息、系统、浏览器版本、电源模式、刷新率、画质、CSS视口及实际渲染分辨率 |
| 参考规格 | 1080p内部渲染、60Hz参考环境、默认画质；记录设备DPR及渲染倍率，不能以更低分辨率的结果冒称1080p通过 |
| 测量范围 | 公开Pages候选版本，累计连续10分钟有效对局运行；提前通关则立即重开续测。必须覆盖首次指令、追逐、抓拖回座、最终允许的最繁忙规则组合和复杂视角 |
| 平均帧率 | 平均至少58FPS，设计目标稳定60FPS |
| 帧间隔尾部 | 前台requestAnimationFrame间隔P95不超过20ms、P99不超过33ms；平均FPS不能掩盖间歇卡顿 |
| 明显停顿 | 没有可重复、由游戏导致的100ms及以上停顿；记录所有此类事件并定位，不随意把最差样本删掉 |
| 样本口径 | 只剔除事先声明的加载页、明确暂停与失焦阶段；规则首次出现、模型动作切换、正常游玩中的突发掉帧必须计入 |
| 重开稳定性 | 重开三次仍无重复事件、残留AI、明显帧率恶化或持续资源增长；不能只测刚打开时 |

默认质量达不到时先优化，必要时降低阴影、渲染倍率、非关键材质与装饰；再用相同场景实测，并记录实际档位与分辨率。低档达标只能报告低档达标，不能掩盖默认档未达标。

首次全面测量可以在前台真实浏览器里完成。无头软件渲染数据、构建通过或GPU模拟不能证明用户设备流畅。requestAnimationFrame间隔是浏览器帧节奏指标，不是物理屏幕的端到端输入延迟。

平均FPS按有效帧数除以有效运行秒数计算，不对每帧瞬时FPS求算术平均；帧间隔分位数保留有效游玩中的长帧样本。

## 4. 手感必须单独检查

- 鼠标转向及时，没有多余缓动造成拖尾；跟随镜头进出墙角不来回抖、不突然跳到另一边。
- 连续走动、斜向、转角、门口、沿墙滑动不粘墙、不抖动；移动速度不随帧率改变。
- 开门、开灯、坐下、起身、甩锅有明确且及时的视觉反馈；按键不积压、不重复触发，不等长动画播完才允许取消。
- 滚椅惯性可控，转弯和停下可预期；“背锅/逆风造成的规则减速”有提示，不能与性能卡顿混淆。
- 规则宣告、HUD更新和透明栏不抢鼠标，不造成停顿或遮挡关键操作；退出手机/菜单后控制正常恢复。
- 饼膨胀、升桌、隔断变化时，碰撞/视线/导航同步；没有物体穿过去后角色突然被弹回的补偿。

前台浏览器操作与录屏用来检查这些现象；若只有自动脚本而没有真实鼠标操作/真人体验证据，须明确相应手感维度未获真人确认，不能编造“玩家觉得丝滑”。数值验收与主观手感记录分开。

## 5. 从开始就避免卡顿

### 首页、加载、入局的流程

用户提出参考《纸间》开场加载资源。本版加载安排：轻量首页先可见、可操作；点击“开始上班”后生成本局布局并加载本局必需资源；资源和场景准备完成、玩家确认进入后才启动十分钟倒计时。具体视觉与阶段布局交给Kimi，不把参考项目的资源体积当目标。

- 分清“下载资源”“解码模型/贴图及动作”“准备场景与首批效果”。各阶段依据真实完成情况显示；字节总量未知时展示阶段与已完成资源数，不伪造百分比。
- 饼、锅、滚椅、角色动作和本局必需UI在开局前就绪；首次规则不要临时等待下载或大量同步准备。
- 本局暂不使用的装饰和后续地图内容不列入必等清单；首页避免先等待全部3D资产。
- 下载失败可重试或返回首页；重开复用同版本已加载资源，并清理上一局对象和监听。
- 缓存按资源版本更新，不能把旧模型与新规则混用；已加载不等于新版本无需校验。
- 加载完成只说明入局准备完成；渲染、镜头、输入、碰撞和未来联机延迟仍分别验收，不能宣称预加载即可保证丝滑。

### 对局内的性能

1. 稳定步进更新碰撞与运动，渲染与模拟解耦；限制卡顿后的追赶步数，避免一次停顿引发更多补帧。按帧读取输入，镜头平滑量与时间有关且不过度缓动。
2. 对局前加载当前局必需的模型、贴图及动作，提前准备材质/常见效果；本局不在线生成资产。首个指令不能临时下载大模型或同步编译整批材质。
3. 家具等尽量复用几何/材质，控制可见对象、贴图和阴影量；动态规则只更新相关碰撞/导航区域，避免每帧全图寻路。AI可分批更新，画面保持连续。
4. 限制实际渲染像素数量，不把高DPI倍率无上限叠加；先保持文字、人物轮廓和规则清楚，装饰与昂贵后处理后置。[Three.js官方高DPI说明](https://threejs.org/manual/pages/responsive.html)
5. UI按必要频率更新文字，不每帧重建全部DOM；重开释放或复用旧资源、移除监听和定时器，避免越玩越慢。

首批必需下载仍以约15MB为优化目标，但它只是加载预算；包小不等于运行不卡，包大也不能解释镜头粘滞。

## 7. 六小时内如何容纳

仓库接入与发布链路在前120分钟随灰盒一起打通，不全部挤到最后。270分钟前停止新增内容；270—315分钟在已发布候选版做功能、策略与流畅度测试；315—335分钟修复；335—360分钟发布最终候选、在该网址复验、整理评委用说明。若最终修复影响玩法/性能，要重测受影响场景；最终候选的10分钟测量不得用修改前旧结果代替。

任何核心或流畅度目标仍未达到，修复优先于装饰；六小时末仍未达标则如实报告，不因为已部署就写“完成且丝滑”。本文件没有承诺未知设备的性能。
