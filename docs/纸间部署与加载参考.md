# 《纸间》的部署、联机与加载参考

检查日期：2026-10-30。用户指定地址：[纸间公开页面](https://zhijian-web-production.up.railway.app/?release=8687c1a3)。仅检查公开页面和客户端发布文件；未创建房间、加入他人对局、连接联机服务器或发送消息。

## 直接观察到的内容

1. 浏览器实际打开了加载页，显示资源下载进度与“约104MB”；随后进入首页，包含单人练习、多人对战、设置。
2. 打开多人入口，页面明确显示“双人联机”，提供创建房间、加入朋友、地图选择和邀请链接。页面说明房主结束时保存云端世界、让朋友离开；这些是产品说明，未实际验证云端存档。
3. 首页加载 `index.js`，通过 `new Engine(config)`、`engine.startGame(...)` 启动，引用 `index.wasm` 与 `index.pck`，属于Godot Web发布产物。
4. WASM为37,700,666字节，PCK为70,733,832字节，合计约103.4 MiB，不含JavaScript。它的资源体量不作为我们项目的目标。
5. 首页及资源响应有 `server: railway-hikari` 与 `x-railway-edge: sin1`。这是经过Railway服务的证据；边缘节点标识不等于证明后端计算实例所在地区。

公开资源：[引擎JS](https://zhijian-web-production.up.railway.app/index.js)、[WASM](https://zhijian-web-production.up.railway.app/index.wasm)、[资源包](https://zhijian-web-production.up.railway.app/index.pck)。没有把这些文件复制进我们的游戏工程。

## 联机方式的证据

公开PCK内编译脚本 `scripts/net/online_flow.gdc` 的常量含网页地址及独立默认连接地址：`wss://paper-server-production-4b68.up.railway.app/ws`，并含房间邀请参数 `?room=`。

`session.gdc` 的符号有 `WebSocketPeer`、`connect_to_url`、`poll`、`send_text`；`codec.gdc` 有JSON编码/解码；相关文件与符号包含本地预测、远端角色、输入发送与状态快照。它们支持“网页客户端通过WSS与独立服务通信、处理房间及同步”的判断。这里只读取了编译产物的符号与常量，不声称拿到了完整原始源码。

示意关系：浏览器下载网页游戏资源；进入联机时，浏览器另连WSS服务，交换房间和游戏状态。公开网页托管与多人同步是两项职责。

## 对我们部署的意义

已选的GitHub Pages适合发布单人网页客户端。未来若增加多人，可以继续由Pages提供网页与模型，另部署一个支持WSS的房间/同步服务。无需仅因为看到别人的联机入口就整体更换托管方案或引擎。

Railway官方说明：可从仓库或镜像部署服务、生成公开域名、提供HTTPS，支持WebSocket。一个可行的未来部署过程是部署联机进程、监听平台提供的端口、生成域名，再让网页客户端连接WSS；这说明可行途径，不是对《纸间》实际配置的还原。

来源：[Railway服务](https://docs.railway.com/services)、[公开网络](https://docs.railway.com/networking/public-networking)、[WebSocket](https://docs.railway.com/guides/sse-vs-websockets)、[GitHub Pages定位](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)。

多人还需决定谁判定领导命令、任务完成、随机地图、甩锅命中和胜负，并验证断线与房主离开；部署一个服务本身不会自动实现这些。当前只做调研，未创建服务、消费套餐或改变首版单人优先范围。

## 可采纳的加载方式

轻量首页 → 开始上班 → 本局资源下载 → 模型/动作/场景与首批效果准备 → 玩家确认进入 → 开始十分钟计时。

进度来自实际下载或已完成资源数；下载、解码、场景准备分别呈现。加载失败能重试，已缓存资源按版本复用。本局必需的饼、锅、滚椅、角色动作和界面提前就绪，避免首次用到才下载。Kimi负责页面表现与可读性。

预加载减少资源首次使用造成的等待，不保证每帧流畅。模型复杂度、渲染、镜头、碰撞和未来网络延迟仍需独立验收。具体规范已写入[上线与流畅度验收](上线与流畅度验收.md)。
