# V3单人版制作计划

更新：2026-10-30。新制作会话已经启动；本文件记录生产安排和最新职责，不断言代码、资产或部署的实时进度。玩法唯一来源为[单人完整玩法V3](../docs/单人完整玩法提案-v3.md)；本文件安排如何制作、验证和交付，不复刻另一套数值。

**最新分工优先：Kimi Work独立负责全部UI、角色/道具/场景外观、模型、动画表现与美术监督，是Tripo资产设计与生成的唯一执行方；Codex负责内在程序、测试、集成与发布。** 原双方可调用Tripo和Codex代执行条款撤回，执行中的Codex应同时读取[视觉职责补充](../CODEX_VISUAL_REFERENCE_ADDENDUM.md)。用户已澄清“手感”是“手板”的语音错误，指UI与建模；移动、镜头和操控程序照旧由Codex负责。

## 1. 交付目标

用约六小时、一位用户依靠AI工具，完成《领导说的都是真的》电脑浏览器单人一局式逃离，并交付已验证的GitHub Pages链接。

正常闭环：18:00坐本人电脑看豆包彩蛋 → 可装忙/离座探索 → 找到任一打卡机 → 打卡保留 → 处理领导规则、甩锅、滚椅和举报 → 找到并打开任一出口 → 实际越界下班。另有超时加班、甩中领导被炒两类结局。

明确取消工时、电脑文件任务、找钥匙、联网、长教学关、局外成长和战斗。首页保留用户要求的“多人模式·待开发”禁用入口，不假装联机已完成。

## 2. 决策与职责

[当前需求](../docs/当前游戏需求.md)记录用户明确选择，[决策处理记录](../docs/待确认决策.md)记录助手补齐的推荐。V3给出每项规则与初值，执行遵循已启动会话中的用户授权，不让实现者临时选任务或模式。

- Codex：规则/状态、房型/地图、输入/镜头、碰撞/导航、对手、UI绑定、集成、整局真实操作、难度和性能验收。
- Kimi Work：首页和全部UI视觉、角色/物件/场景外观、模型、全部动画姿态与特效表现、Tripo设计/生成及全程美术监督。独立决定视觉风格，不设计房型/机制，不承担完整游玩测试。
- Tripo CLI/API只由Kimi执行，生成登记和输出目录集中。已提交任务按明确ID/状态登记，保留现有结果交Kimi判断，不盲目取消或重复生成；本次文档修正不接管运行进程。此前3000积分、冻结0与仓库空状态只是查询快照，不能推断新会话启动后的余额、生成或发布进度，详见工具文档。
- Codex可用最小灰盒验证玩法、空间和操控，不能替代或预定视觉成品；Kimi未就绪时继续内在程序，不自行做UI、建模或Tripo。双方可只读学习 `/Users/yb/Desktop/Name/Zcode/设计/Kimi提示词库`，由Kimi自己选参考；用户认可办公室案例逼真，不等于指定照搬。
- 用户是唯一人类制作成员；不把AI并行写成拥有多名真人的产能保证。

## 3. 技术与最小模块

Vite＋TypeScript＋Three.js，HTML/CSS显示UI；本版不建后端、不运行在线LLM。第三方库属于工具，具体版本在正式开工按官方说明锁定。

| 模块 | 责任 |
| --- | --- |
| contracts | 只读状态、命令、事件、资源ID和碰撞尺寸；Codex统一维护 |
| rules | 唯一局时、打卡/出口、追责/规则、冲刺、锅归属、椅状态、胜负 |
| world | 固定房型模板、种子生成、可达性、灯区、动态占位与导航 |
| gameplay | 输入、第三人称、移动/坐椅、抓拖、物件交互、AI感知 |
| ui/theme + ui/views | Kimi的主题/页面/动效，只读映射后的数据 |
| ui/bindings + app | Codex把UI命令和状态接入唯一规则，管理加载/暂停/错误/重开 |
| presentation | Kimi Work独立制作网格、材质、动画与全部美术表现，不持有判定 |
| assets/source + runtime | Kimi负责原始与运行模型、生成/处理/导出和美术记录；Codex负责资源映射、技术检查与集成 |

状态中不再有工时或工作文件任务。动画表现收到语义事件，命中/抓取/打卡完成由规则决定；不由美术动画回调擅自改变事实。

使用简单角色/家具碰撞代理与可查询的空间分区；动态规则只更新受影响导航，领导依据已知信息寻路。模型不作为唯一碰撞定义，规则看见的范围与画面一致。

## 4. 页面与加载

首页 → 加载/重试 → 开始本局 → 真实对局 ↔ 暂停 → 正常下班/被留加班/被炒 → 同种子重玩/新办公室/首页。

教程三页分别解释移动观察与装忙、打卡出口与灯、规则与锅/椅，包含按键与简短动作示意。新局不锁玩家阅读长说明。

轻首页先可见；点击开始后加载本局必需模型/动作/UI，准备场景及首次效果。按真实阶段报告进度，准备完成前不计时。首次规则不临时下载大资源；重开复用同版资源并清理旧局对象。

手机查看时世界继续，Esc/浏览器失焦则单人全局暂停；恢复必须点击继续，不能恢复瞬间误投或计时跳变。所有交互区分指针锁定与页面焦点。

## 6. 动作与资源管线

详见[工具与资产调用](../docs/工具与资产调用.md)和[Kimi简报](../docs/Kimi美术与UI简报.md)。先验证统一角色的尺寸、骨骼与挂点，再扩领导和同事外观；人物尽量共享动作骨架。锅/饼和椅子应有清楚轮廓与分件，动态变形由程序驱动。

常规动作可循环、可打断；拖回才有明确2—4秒失控演出。收锅、投掷、飞行、附着、记仇反馈之间状态同步，坐姿换头顶挂点不能复制锅。美术插值不改变命中时刻。

性能从灰盒开始：限制像素比、动态阴影、模型/贴图、透明效果与寻路频率；资源首局准备；避免每帧重新建立UI。下载预算和游戏帧率分别记录。

## 7. 有意义的验证

### 自动检查

围绕真实风险覆盖：未打卡不能离场、打卡后被抓仍保留、正常/超时/被炒三结局互斥、暂停无跳时；锅唯一归属和一人一锅、投空回归、已有锅不交换；暗室抓取中止、报告保留旧位置、不靠声音或隐藏玩家坐标；同种子布局复现、多种子站姿/滚椅可达、动态恢复不封路。

不写仅镜像实现或无意义凑覆盖率的测试。构建/typecheck与这些规则检查分别报告。

### 实际浏览器操作

固定三个种子，每个做三种约90秒开局片段：先探索、先装忙观察、直接尝试打卡/门，共约14分钟。另做两场完整对局，最多20分钟；余下时间定点检查抓回、锅、暗室/开关和门。帧数据同步收集，避免另占完整局时间。

片段不等于已测通关率；两局不等于全人群难度平衡。有条件请用户或其他首次玩家做一局盲测，记录其迷路、理解和失控点；没有真人反馈就明确缺失，不编造“玩家评价好玩”。

重点反例：连续Shift绕圈、面前开门的预警时间差、切灯循环、坐下洗证据、免疫强开门、同事报告实时追踪、锅复制/自卸、椅子窄门、顶板/桌复位挤压、双门共享瓶颈。

### 难度调整顺序

过易：先查对手是否真的看得到/走得通、任务点分布和绕路是否有选择，再调整巡逻停留与常规命令间隔。过难：先修误判/过期追责/连控，再降低同时干扰和追查频率。保持打卡永久、暗室保护、预警和滚椅可达，不用额外钥匙或清空进度弥补。

用户要求的是适中且紧张，不能以策划数值自证。记录每次被抓原因、首次发现打卡机/出口的时间、是否理解预警、主动改道和正常通关用时；不把随机运气误称难度。

## 8. 公开发布与流畅度

使用既有公开仓库[0505ttt/leadership-always-right](https://github.com/0505ttt/leadership-always-right)，GitHub Pages默认域名，不购买服务器/域名。Vite base为 `/leadership-always-right/`。连接/提交推送/Actions与Pages公开发布已授权，不自动代发评委或代填赛事表单。

[上线与流畅度验收](../docs/上线与流畅度验收.md)为唯一具体性能口径：真实参考设备/浏览器/分辨率/画质，1080p/60Hz默认质量目标平均≥58FPS、帧间隔P95≤20ms、P99≤33ms，无可重复100ms以上游戏停顿。公开最终候选累计10分钟有效对局，包含首次效果、追逐、拖回、允许组合和重开；三次重开不持续恶化。

镜头、输入、碰撞、滚椅和动作响应单独观察。只测无头或本地不声称已验证评委设备；降低画质后的数据单列。公开可访问、可通关、流畅三个结果分别记录。
